# Captive onboarding deadline

A positive captive-network check may temporarily suspend fail-closed steering so the user can sign in to the local network. The signed configuration's `captive-timeout` is a security deadline for **new direct connections**, not a maximum lifetime for established sessions. `captive-probe-interval` controls recovery probes and the advance start of local rearm. Neither setting changes TLS, device identity, or policy verification.

Before suspending steering, the current fail-closed WFP owner arms a kernel monotonic deadline. Normal policy SET/CLEAR, owner replacement, process death and service stop do not clear or extend it. ARM version 2 returns the original generation and remaining time. The controller subtracts acknowledgement/readback latency and starts rearm one probe interval before expiry, capped at half the remaining window. An already-expired acknowledgement never opens native networking. A blocked probe cannot delay the rearm timer; production probes bound each network wait to four seconds (TCP dial, TLS handshake, CONNECT exchange), closing their socket on return. The controller starts no second probe while one is outstanding; local certificate verification and diagnostic I/O are not claimed to have a wall-clock deadline.

After expiry, four ALE authorization gates in a dedicated sublayer refuse new outbound and inbound flows. The separate sublayer prevents an ordinary inbound terminating permit from skipping the deadline gate through same-sublayer arbitration. They do not filter every IP packet or reset established TCP/UDP sessions. Reconnects and a UDP socket's new remote peer need a new admission. Ordinary DNS, browser traffic, and configured bypass applications do not gain a deadline exception. The exceptions are loopback; DHCPv4/DHCPv6, IPv6 neighbor/router and multicast listener control, and IP error/PMTU control; and the owner agent's TCP connections to the exact verified-profile Edge IP/port pins. The Edge recovery list is independent of general bypass destinations. Process-exit notification revokes the recovery PID before reuse; no process notification support means ARM is refused.

## Established flow evidence

Two `ALE_FLOW_ESTABLISHED` observers allocate a context per WFP flow. Contexts are associated at that same layer and its registered runtime callout ID. The admission lookup requires the flow handle, transport endpoint handle, compartment, IP family, protocol, local/remote addresses and ports to match. The bucket count is an indexing choice, not a connection limit. There is no fixed entry count or session-age cutoff.

A reauthorization flag alone is insufficient: a previously pended *new* connection also carries that flag. `CLASSIFY_COMPLETION` is therefore refused as established evidence even when mixed with another reason. For flows predating the observer or missing a record because allocation/association failed, the fallback requires nonzero WFP flow and endpoint handles and a recognized established-connection reason (policy/interface/profile/IPsec/midstream/socket-property change). Unknown reasons and known-handle tuple mismatches cannot use this fallback. The driver asserts the portable decision constants against the WDK definitions at build time.

WFP `flowDelete` removes the record on actual flow termination, including reset. The endpoint and full tuple prevent one UDP peer or reused TCP endpoint from inheriting another flow's record. FINISH does **not** erase records: native flows must also survive the normal QUIC/inbound reauthorization caused by rearm. A recorded tracking gap retains the same strict WFP established-flow fallback after FINISH; it never authorizes a new initial or pending-completion request. This preserves existing flows without a newly imposed lifetime limit. For the WFP backend, rearm uses the driver's ALE QUIC gate instead of reinstalling a blanket Windows Firewall UDP/443 rule that would cut existing QUIC flows.

## Lifetime and shutdown

An extra reference keeps a context alive while association races natural flow deletion. Only `STATUS_SUCCESS` transfers ownership; informational `STATUS_OBJECT_NAME_EXISTS` retires the duplicate allocation. On unload, DSSE closes the dynamic filter engine, prevents new associations and waits for their rundown, removes every WFP context, then unregisters the callouts. `FwpsFlowRemoveContext` success invokes deletion synchronously; `STATUS_PENDING` completes asynchronously; `STATUS_UNSUCCESSFUL` can accompany concurrent natural deletion. The code retains ownership and retries outstanding removal, logging unexpected errors. It never frees a context still owned by WFP or forces unregister past outstanding contexts. A persistent unexpected WFP removal failure therefore prevents safe unload and requires diagnosis; this must be exercised with Driver Verifier before acceptance.

The guard is independent of the **service**, not of driver unload or reboot. Explicit elevated recovery clears and verifies it before driver removal. A plain service stop retains the unfinished generation and deadline. No new resources, authentication relaxations or automatic reconnects are introduced by these rules.

## Verification and release boundary

Portable C tests execute the actual admission, flow association/deletion and reauthorization functions through WFP boundary shims. Registration tests exercise the actual action types and reject a mutation back to terminating callouts. Go tests cover inherited remaining time, expired acknowledgement, pre-deadline rearm, blocked probes, failed rearm and owner/publication sequencing. These tests do not prove WFP runtime behavior or replace a WDK build.

The existing driver project targets `NTDDI_VERSION=0x0A000008` (Windows 10 version 2004/VB) and already uses `ExAllocatePool2` for redirect contexts. Flow records use the same zeroed nonpaged allocator; this change does not raise that existing build target. The allocator requires Windows 10 version 2004 or later; see [Microsoft’s pool API guidance](https://learn.microsoft.com/en-us/windows-hardware/drivers/devtest/codeql-windows-driver-wdkdeprecatedapi). A broadly worded Windows 10 support claim is not proof that pre-2004 releases work.

Before distribution: build with the supported WDK; run Driver Verifier/IRQL and concurrent flow-delete/unload tests; exercise pre-driver and pre-ARM TCP/UDP flows, endpoint/tuple reuse, different UDP peers, pending completion at the deadline, allocation fault, owner death/service stop, Edge recovery, DHCP/IPv6 control and FINISH reauthorization on Windows. Confirm that existing connections continue while new direct connections fail. Obtain new Microsoft driver signing and signed MSI payloads. None of those Windows or signing checks is claimed by the host tests.

The implementation follows Microsoft's [ALE reauthorization contract](https://learn.microsoft.com/en-us/windows/win32/fwp/ale-re-authorization), [reason flags](https://learn.microsoft.com/en-us/windows/win32/fwp/filtering-condition-flags-), [metadata by layer](https://learn.microsoft.com/en-us/windows-hardware/drivers/network/metadata-fields-at-each-filtering-layer), [flow context association](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fwpsk/nf-fwpsk-fwpsflowassociatecontext0), [flow deletion callback](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fwpsk/nc-fwpsk-fwps_callout_flow_delete_notify_fn0), [context removal](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fwpsk/nf-fwpsk-fwpsflowremovecontext0), and [callout unregister requirements](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/fwpsk/nf-fwpsk-fwpscalloutunregisterbyid0).
